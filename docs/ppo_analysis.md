# PPO：从崩溃到修复的完整排查记录

这是整个项目里花时间最多的一部分，单独整理出来。核心事实：用跟 GRPO 完全对齐的超参跑 PPO，第一次直接训崩了；分析原因、改了几个地方之后修复成功；修复之后又反过来做了一次 KL 系数消融，发现了一个不太符合直觉的结果。三件事按顺序讲。

## 1. 崩溃是怎么发生的

**实验设置**：PPO 和 GRPO 用同一个 SFT checkpoint 初始化，同样的 `train_batch_size=256`、`ppo_mini_batch_size=64`、`actor_lr=1e-6`、`kl_loss_coef=0.001`，PPO 额外加上 `critic_lr=1e-5`、`gamma=1.0`、`lam=0.95`（GAE）、`rollout.n=1`、`critic_warmup=0`。目的是尽量控制变量，只让"有没有 critic"这一个因素不同。

**发生了什么**：训练刚开始几步就不对劲。

| step | val reward@1 | response_length/mean | clip_ratio |
| --- | --- | --- | --- |
| 0 | 0.129 | - | - |
| 5 | -0.934 | 183 | - |
| 20 | 崩溃持续 | 1024（打满上限） | 100% |

validation reward 五步之内从 0.13 掉到 -0.93，response length 二十步之内从 183 拉到 1024（`max_response_length` 上限，也就是每条都被截断），`clip_ratio` 打到 100%。此后模型没有再恢复，稳定在"每次都生成到截断"的退化解，最终评估 pass@k 为 0%。

## 2. 根因分析

PPO 相比 GRPO 多了一个 critic，这个 critic 是随 actor 一起从零训练的，训练最早期它对 value 的估计是不准的（`vf_explained_var` 起始值是 -2.27，负数意味着比"直接猜均值"还差）。GAE 算出来的 advantage 依赖这个不准的 value 估计，本质上前几步的 advantage 信号里噪声占比很高。

这里的关键问题是：如果某一次更新恰好让"生成更长"这个方向拿到了正的 advantage（哪怕只是 critic 早期误判导致的巧合），策略梯度会顺着这个方向继续加强，而当时的 reward 设计里，对被截断的样本只有一个固定的 -1 惩罚，跟"正常生成但答案错误"的惩罚是一个量级，起不到"重罚拉长行为"的作用。于是这个方向一旦被误判为好方向，就没有足够强的负反馈把它拉回来，最终整个训练滑向"无脑拉满长度"的退化解。

反过来看 GRPO 为什么没有这个问题：GRPO 用同一个 prompt 的一组 rollout（这里是 8 条）内部相对排名做 baseline，完全不需要一个额外学出来的 value 函数。也就是说 GRPO 不存在"critic 早期不准导致 advantage 是噪声"这个环节，天然对这类问题更鲁棒。这是这次崩溃复盘里最想弄明白、也确实想清楚的一点——GRPO 的稳定性优势不是偶然，是算法结构上就少了一个不稳定的来源。

## 3. 修复方案

针对上面分析出的两个问题（critic 早期不可靠、截断惩罚力度不够），做了这几处改动：

| 参数 | 修复前 | 修复后 | 目的 |
| --- | --- | --- | --- |
| `critic_warmup` | 0 | 20 | 前 20 步只更新 critic 不更新 actor，让 value 函数先具备基本的预测能力，再让它参与指导策略更新 |
| `kl_loss_coef` | 0.001 | 0.01 | 加大 KL 惩罚，限制策略早期偏离 SFT 分布的速度，压缩"投机"空间 |
| `critic_lr` | 1e-5 | 5e-6 | 降低 critic 学习率，减少价值函数自身的早期震荡 |
| `critic.cliprange_value` | 0.5 | 0.2 | 收紧价值函数单步预测的跳动幅度 |
| `rollout.temperature` | 1.0 | 0.7 | 降低采样温度，减少 rollout 方差 |
| 截断额外惩罚 | 无 | `truncated_extra_penalty=2.0` | 对被截断（提取不到 answer 且长度比例超过阈值）的样本施加比普通答错更重的惩罚 |
| 长度惩罚起始比例 | - | `length_penalty_start_ratio=0.9` | 长度超过上限 90% 时就开始施加渐进惩罚，而不是等真正截断才罚，让负反馈更早出现 |

截断惩罚这部分的具体实现在 `reward/rule_reward.py` 的 `RuleReward.score` 里，逻辑是：如果提取不到 `<answer>` 且 `response_length_ratio` 超过 `length_penalty_start_ratio`，惩罚随长度线性增长，长度打满上限时惩罚达到最大值。同时改了 `verl/workers/reward_manager/naive.py`，让它用 `inspect.signature` 检测自定义 `compute_score` 是否接受 `response_length_ratio` 参数，接受的话就把这个信息传进去——这样改动只对开启了截断惩罚的 PPO 生效，不影响已经跑通的 GRPO 路径。

**修复后的训练过程**：

| step | val reward@1 | response_length/mean | clip_ratio | vf_explained_var |
| --- | --- | --- | --- | --- |
| 0 | 0.129 | - | - | - |
| 20（warmup 结束） | ~0.35 | ~200 | ~5% | ~0.55 |
| 28（长度冲高峰值） | - | ~348 | ~8% | ~0.60 |
| 60 | ~0.36 | ~150 | ~0% | ~0.70 |
| 116（最终） | 0.358 | 85 | 0% | 0.634 |

中间在 step 21-28 之间其实还是出现了一次 response length 冲高（到 348），这是 critic warmup 结束、actor 开始真正更新时的正常探索行为，本质上跟第一次崩溃时的起因是同一类。区别在于这次冲高之后，`clip_ratio` 回落到 0，reward 也跟着回升，模型自己把这次探索"收"了回来，而不是像第一次那样一路滑向退化解。这个"探索、冲高、自我修正"的完整曲线，跟第一次的"冲高、再未回落"放在一起看是最直观的对比，图见 `docs/images/ppo_collapse_vs_fixed.png`。

最终 GSM8K pass@1 到了 42.6%，MATH 31.2%，虽然明显低于 GRPO 的 67.7%/48.8%，但相比崩溃版本的 0% 是质变。

## 4. 修复之后：KL 系数消融的反直觉结果

修复方案定下来之后，很自然地想确认一下 `kl_loss_coef=0.01` 这个值是不是必须的、能不能再调优。于是在其余配置完全不变（`critic_warmup=20` + 截断惩罚 + 更紧的 critic clip）的基础上，只改 KL 系数，跑了 0.005 和 0.02 两组对照。

| kl_loss_coef | GPU | GSM8K pass@1 | val reward@1（最终） | 是否出现长度失控 |
| --- | --- | --- | --- | --- |
| 0.005 | 2卡 | 61.9% | 0.505 | 否，全程 60-130 平稳 |
| 0.01（4卡，主实验） | 4卡 | 42.6% | 0.358 | 是，step 21-39 冲到 1024，之后回落并稳定 |
| **0.01（2卡，受控对照）** | 2卡 | **2.4%** | **-1.258** | **是，且更严重：反复冲高，直到训练结束都没能完全稳定** |
| 0.02 | 2卡 | 62.1% | 0.503 | 否，从 100 缓慢升到 190，无失控 |

本来预期是"KL 越大越保守越稳"，结果完全不是这么回事：0.005 和 0.02 这两个明显更"紧"或更"松"的值全程都很平稳，效果也都在 61%-62% 左右（比主实验的 42.6% 好不少），偏偏中间的 0.01 会崩——而且专门补做了一次 2 卡的受控对照实验（排除"是不是 4 卡训练偶然巧合"这个疑问），发现 2 卡上 0.01 崩得更彻底，训练全程都没能稳定下来。

目前的理解是：这个具体配置下，0.01 这个取值恰好落在"critic 刚结束 warmup、对某个 mini-batch 里变长样本的 advantage 判断"和"策略更新幅度"两者共振的一个不稳定区间里。定量看，step 21 附近 KL 系数为 0.01 时，`kl_loss` 对总 loss 的贡献量级只有 0.0002-0.0003，远小于同期的策略梯度项——也就是说在这个关键节点，KL 惩罚本身的绝对大小在 0.005~0.02 这个范围内其实都不算大，真正决定是否滑向崩溃的可能是 critic 在那个具体 batch 上给出的 advantage 符号，KL 系数更像是影响"滑向哪个吸引域"的一个扰动量，而不是单调的安全阀。

这个解释目前还只是一个猜测，如果要坐实还需要用不同随机种子对 0.01 重复跑几次，看崩溃是不是稳定复现——这部分受限于时间还没有做，先如实记录在这里。**实践结论是**：至少在这套训练配置下，不建议用 0.01 作为默认 KL 系数，0.005 或 0.02 都是更安全的选择。

训练曲线见 `docs/images/ppo_kl_ablation_curves.png`（及局部放大图 `ppo_kl_ablation_curves_zoom.png`），四组曲线在 step 21 之前逐位重合（说明用的是同一个随机种子和数据顺序），分岔点精确发生在 step 21-22。
